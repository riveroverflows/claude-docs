# Requirements Writer Skill

이커머스 프로젝트 전용 요구사항 정의서 작성 스킬. 매 주차 과제마다 일관된 품질의 요구사항 문서를 생성한다.

## 대상 프로젝트

- E-Commerce 프로젝트 (`/Users/river/Developer/loopers/e-commerce`)
- `docs/CLAUDE.md` 작성 규칙 준수
- 용어집(`00-ubiquitous-language.md`) 연계
- 프로젝트 CLAUDE.md의 패턴/컨벤션 참조

## 워크플로우 (5단계)

### Step 1: 과제 읽기 & 도메인 식별

**목표**: 과제/PRD 문서를 분석하고 핵심 컨텍스트를 파악한다.

**작업**:
1. 과제/PRD 문서를 읽는다 (파일 경로가 제공되면 Read, 텍스트로 제공되면 직접 분석)
2. 도메인, 액터, 핵심 기능을 식별한다
3. 기존 프로젝트 컨텍스트 확인:
   - `/Users/river/Developer/loopers/e-commerce/CLAUDE.md`
   - `/Users/river/Developer/loopers/e-commerce/docs/design/00-ubiquitous-language.md`
   - `/Users/river/Developer/loopers/e-commerce/docs/CLAUDE.md` (작성 규칙)

**출력**: 도메인/액터/기능 요약 → 사용자 확인

### Step 2: 대화형 요구사항 명확화

**목표**: 애매한 요구사항을 구체화하고 Scope를 결정한다.

**판단 기준**: "이 조건을 보고 테스트 코드를 바로 작성할 수 있는가?"

**작업**:
1. 애매한 요구사항 식별:
   - "충분하다", "유효하다", "적절하다" 같은 추상적 표현
   - 숫자로 표현 불가능한 조건
   - 여러 해석이 가능한 문장
2. `AskUserQuestion` 도구로 질문 (예시):
   - "재고 충분"이 정확히 무슨 뜻인가? (주문 수량 ≤ 재고 수량?)
   - "유효한 사용자"의 조건은? (이메일/비밀번호 일치?)
   - 재고 부족 시 동작은? (주문 전체 실패? 부분 주문?)
3. Scope 결정 (구현 vs 제외):
   - 구현할 것: 명확한 인수조건으로 정의 가능
   - 제외할 것: 근거 + 대안 명시 필수

**출력**: 명확화된 요구사항 목록 + Scope 결정 사항

### Step 3: 문서 구조 설계

**목표**: 도메인별 그룹핑으로 시나리오와 요구사항을 배치한다.

**작업**:
1. 도메인별 그룹 식별 (예: 브랜드/상품 탐색, 좋아요 관리, 주문 생성, Admin 관리)
2. 각 그룹의 시나리오 정의:
   - 목표 (액터의 독립된 목표)
   - 사전조건 (필요시)
   - 기본 흐름 (정상 케이스)
   - 예외 흐름 (실패 케이스)
3. 시나리오에서 기능 요구사항 추출
4. Mermaid 다이어그램 설계:
   - 역할별 접근 흐름 (flowchart LR)
   - 주요 액터 전체 여정 (flowchart TD)

**출력**: 문서 구조 개요 → 사용자 확인

### Step 4: 문서 작성

**목표**: 아래 템플릿에 따라 요구사항 정의서를 작성한다.

**작업**:
1. 아래 "문서 구조 템플릿" 참조
2. `docs/CLAUDE.md` 작성 규칙 준수 (하단 참조)
3. 구체적 표현 사용:
   - "충분하다" → "주문 수량 ≤ 재고 수량"
   - "유효하다" → "이메일/비밀번호가 일치한다"
   - "오래된" → "생성일로부터 30일 경과"
4. 번호 없이 도메인별 그룹핑 (FR-001 같은 라벨링 불필요)
5. Scope 제외 항목에는 반드시 근거 명시

**출력**: 완성된 요구사항 정의서 초안

### Step 5: 검증 & 확정

**목표**: 문서 품질을 검증하고 사용자 최종 확인을 받는다.

**작업**:
1. 아래 체크리스트로 문서 검증
2. 누락/불명확 항목 보완
3. 사용자 최종 확인

**출력**: 확정된 요구사항 정의서

## 핵심 원칙 (7가지)

### 원칙 1: 요구사항 문서 ≠ 기획서

| 구분 | 목적 | 길이 |
|------|------|------|
| 기획서 | "왜" 만드는가, 사용자 경험 | 길어도 됨 |
| 요구사항 정의서 | "무엇을" 만드는가 | 짧고 명확 |

**적용**: 사용자 경험, 시장 분석, 비전은 제외. 시스템이 해야 할 동작만 기술.

### 원칙 2: 시나리오는 수단, 요구사항이 본체

- 시나리오: 1페이지 이내 요약 (목표, 흐름만)
- 기능 요구사항: 시나리오에서 추출한 구체적 조건들

**예시**:
```
시나리오: Customer가 상품을 주문한다.
기능 요구사항:
- 주문 수량 ≤ 재고 수량이면 주문이 성공한다.
- 주문 수량 > 재고 수량이면 주문이 실패한다.
- 주문 성공 시 재고가 주문 수량만큼 차감된다.
```

### 원칙 3: 유스케이스 사고 (화면 흐름 X)

- "사전조건: 상품 목록이 결정되어 있다" ← 어떻게 결정했는지는 관심사 밖
- UI 세부사항 배제 (버튼 위치, 색상, 레이아웃 등)
- 관찰 가능한 시스템 동작에 집중

**판단 질문**: "백엔드 API만으로 이 요구사항을 검증할 수 있는가?"

### 원칙 4: 비즈니스 규칙 vs UI 동작 분리

**판단 질문**: "프론트엔드가 바뀌어도 이 규칙은 유지되는가?"

| 유형 | 예시 | 포함 여부 |
|------|------|----------|
| 비즈니스 규칙 | 재고 초과 주문 불가 | O |
| 비즈니스 규칙 | 주문 성공 시 재고 차감 | O |
| UI 동작 | alert를 띄운다 | X |
| UI 동작 | 버튼 색상을 변경한다 | X |

### 원칙 5: 번호 없이 도메인별 그룹핑

- FR-001, UC-003 같은 라벨링 불필요
- 도구 없이 수동 관리 시 부담만 증가
- 마크다운 헤더(`###`)로 그룹핑이면 충분
- 도메인/목표별로 자연스럽게 섹션 나누기

**예시**:
```markdown
### 4.1 브랜드/상품 탐색
### 4.2 좋아요 관리
### 4.3 주문 생성 및 조회
```

### 원칙 6: Scope 제외 시 근거 명시

**나쁜 예**:
```
결제는 제외한다.
```

**좋은 예**:
```
결제는 본 문서의 범위에서 제외한다. 이유는 결제 프로세스가 복잡하고
외부 PG사 연동이 필요하므로, 별도 설계 문서로 다룬다. 본 문서에서는
주문 생성까지만 다루며, 결제는 추후 확장 포인트로 남긴다.
```

### 원칙 7: 유스케이스 분리 기준

**질문**: "액터의 독립된 목표가 있는가?"

| 상황 | 판단 | 이유 |
|------|------|------|
| Customer 브랜드 조회 | 상품 탐색과 합침 | 상품 탐색의 수단일 뿐 |
| Admin 브랜드 조회 | 별도 유스케이스 | 관리 목적으로 독립적 |
| Customer 좋아요 등록 | 별도 유스케이스 | 구매와 무관한 독립 목표 |

## 검증 체크리스트

문서 작성 후 다음 항목을 검증한다:

### 구체성 검증
- [ ] 모든 조건이 숫자/조건식으로 표현 가능한가?
- [ ] "충분하다", "유효하다" 같은 추상적 표현이 없는가?
- [ ] 각 조건을 보고 테스트 코드를 바로 작성할 수 있는가?

### 범위 검증
- [ ] In Scope가 명확히 나열되었는가?
- [ ] 제외 항목에 근거가 명시되었는가?
- [ ] 범위 고정 문장이 포함되었는가?

### 작성 규칙 준수
- [ ] API/HTTP/DB 같은 구현 용어가 없는가?
- [ ] 사용자 시나리오와 비즈니스 규칙에만 집중했는가?
- [ ] UI 동작("버튼 클릭", "alert 표시")이 배제되었는가?

### 문서 구조
- [ ] 도메인별 그룹핑이 적절한가?
- [ ] 시나리오가 1페이지 이내로 요약되었는가?
- [ ] Mermaid 다이어그램이 포함되었는가?
- [ ] 비즈니스 규칙이 별도 섹션으로 정리되었는가?

### 용어 일관성
- [ ] 00-ubiquitous-language.md와 용어가 일치하는가?
- [ ] 동일 개념에 여러 용어를 사용하지 않았는가?
